# TPP-mark 2026：4×4・6×6 Othello

[English](README.md) | [日本語](README-ja.md)

## 作成方法

[TPP-mark 2026](https://auto-res.github.io/tpp2026/ja/tpp2026mark/) の4×4・6×6 Othelloの課題に対する，Rocqで記述した解答です．
実装，証明，証明書の生成器，文書の作成と修正にCodexを使いました．

戦略の探索には，Rocqとは別に実行するプログラムを使いました．4×4では同梱のPythonプログラム [generate_certificate.py](generate_certificate.py)，6×6ではこのプロジェクト用に作成したCプログラムを使用しました．
これらのプログラムは，選んだ手と相手の応手をデータとして記録します．このデータを「戦略の証明書」と呼びます．

Rocqは証明書を読み，着手がルールに従っているか，終局時に求める石数の条件を満たすかを検査します．
証明には，この検査の結果と，検証器が受理したデータは正しい戦略を表すという定理を使います．
開発時に使ったプログラムと，結果を検査するために必要なデータについては，[6×6の証明書の説明](6x6/README-ja.md#certificate-data)を参照してください．

## 証明したこと

問題文と証明は **[4×4](solutions/Othello4x4.v)**・**[6×6](solutions/Othello6x6.v)** にあります．
両サイズに共通するルールは[共通ルールの説明](common/README-ja.md)を参照してください．
各ファイルに初期盤面，問題を表す定義 `problem`，その証明 `solution` をまとめています．

| 盤面 | 結果 |
|---|---|
| 4×4 | 黒のどの合法な戦略に対しても，白は勝利を保証できる |
| 6×6 | 双方が最善手を選び続けると，終局時の黒石数−白石数は−4 |
| 6×6の具体例 | 32手すべてが最善手で，黒16石・白20石で終わる |

6×6では，`solution` が黒は−4以上，白は−4以下を保証できることを証明します．
`optimal_line` は，示した対局の各手が最善手で，黒16石・白20石で終わることを証明します．
一般の対局についての定理は，合法な着手や強制パスのたびにゲームの値を保ち，終局まで続く有限の対局を対象とし，終局時の石数差が−4になることを示します．
黒16石・白20石という個別の石数は，示した対局について証明しています．

## ソース配布

配布物はソースだけで，`.vo` やコンパイル済みプラグインは含みません．
小さいソースファイルはGitで管理しています．容量の大きい6×6の生成済み証明書ソースは，**5個の `.tar.gz` ファイル（合計約2.92 GB）** にまとめています．
[収録一覧と取得手順](distribution/README-ja.md#certificate-archives)を参照してください．

**6×6の証明のビルド・検査には，別添の証明書ソースが必須です．Git内のファイルだけでは完結しません．**
別添には，主定理で使う戦略データと証明を収録しています．これらのソースも証明の一部です．
4×4の証明全体はGitに含まれています．

| ディレクトリ | 内容 |
|---|---|
| `common/` | 共通ルール，戦略の定義，補助補題 |
| `boards/` | 共通定義を各サイズに具体化 |
| `solutions/` | 初期盤面，問題文，主定理 |
| `4x4/`・`6x6/` | 証明書の検査で使うルール，検証器，解答の証明 |
| `proofs/equivalence/` | 証明書側のルールと共通定義の同値性の証明 |
| `proofs/certificates/` | 検査済み証明書の結果を共通定義で導く |
| `distribution/` | 収録一覧，ハッシュ，文書の検査，ビルド記録 |

両サイズの `Rules.v`・`Bounds.v`・`CertificateResult.v`・`RulesExamples.v` は，それぞれ同じ役割です．
4×4の小さい証明書は `4x4/Certificate.v`，6×6の証明書は多数のファイルに分割されています．
`6x6/OptimalPlay.v` では，具体的な対局の各手が最善手であることを証明します．
`solutions/` は共通定義を使った問題文と証明，`4x4/CertificateResult.v`・`6x6/CertificateResult.v` は証明書側の定義による結果を扱います．
ディレクトリ `4x4/`・`6x6/` は，`_CoqProject` とビルドスクリプトでRocqの名前空間 `TPP2026.Four`・`TPP2026.Six` に対応付けています．

## ビルドと検査

Rocq 9.2 / OCaml 5.3.0，Python 3.11以降，GNU makeを使用します．
スクリプトはUnixのファイルロックとファイルシステムのハードリンクを使用します．
`rocq` をPATHに置くか，コマンドに `ROCQ=/absolute/path/to/rocq` を追加します．
6×6ではRocqと同じツールチェインの `ocamlfind`・`ocamlopt` を使用します．
既定ではRocqの実行ファイルと同じディレクトリにある `ocamlfind` を使います．別の場所は `OCAMLFIND=/absolute/path/to/ocamlfind` で指定できます．
リポジトリのルートから実行してください．

4×4の証明全体は，Gitに収録したソースだけで検査できます．

```text
make check-4x4
```

**6×6の初回のビルド・証明検査には数時間を見込んでください．**
以前の版で，Rocq 9.2 / OCaml 5.3.0と `JOBS=8 LINK_JOBS=1 INTERFACE_JOBS=4` を使って両サイズをソースから初めてビルドした際は，約 **5時間26分** かかりました．
その大部分は6×6の処理です．所要時間はマシンと設定により変わります．
この実測には，追加の6×6全体の公理監査・カーネルによる再検査を含みません．

**ビルドスクリプトは，6×6の初回ビルド前に，ソース展開後の空き容量が70 GB以上あることを確認します．**

6×6を検査する場合は，[取得手順](distribution/README-ja.md#certificate-archives)に従って5個全ての証明書アーカイブを入手します．
入手後，`/path/to/archives` をダウンロードしたファイルの保存先に置き換え，次を実行してください．

```text
make unpack-certificates ARCHIVE_DIR=/path/to/archives
make check-disk
make check-certificate-files
make check-6x6
```

展開コマンドは，全アーカイブを確認してからソースを書き出し，各ファイルを収録一覧と照合します．証明書ディレクトリが既にある場合は停止するため，ソースを用意済みならこのコマンドを省略してください．
両サイズを検査する場合は `make check` を使います．`make check-disk` は空き容量，`make check-certificate-files` はソースのサイズ・ハッシュを確認します．これらの準備用コマンドは証明を検査しません．

中断後の再開や，同じディレクトリで4×4の検査後に6×6を追加する場合にも使えます．
新規または空のビルドディレクトリから始めることを確認したい場合は，ビルドのコマンドに `FRESH=1` を追加してください．
ソースからプラグインをビルドし，分割した証明書を検査して，それらが一つの戦略を構成することを証明し，主定理までコンパイルします．
4×4を検査する場合は，その結果をカーネルで再検査します．
ビルドの生成物と記録は，既定ではソース配布対象外の `_build/` に置きます．

| コマンド | 範囲 |
|---|---|
| `make check-4x4` | 4×4の定義と証明をビルドし，カーネルで再検査 |
| `make check-6x6` | 全証明書ブロックを含め，6×6の定義と証明をビルド |
| `make check` | 両方を実行 |
| `make audit-6x6` | 6×6をビルドし，主定理と全依存先の公理を監査 |
| `make kernel-6x6` | 6×6をビルドし，全体をカーネルで再検査 |
| `make check-archives ARCHIVE_DIR=/path/to/archives` | 展開せずにアーカイブのサイズとSHA-256を確認 |
| `make unpack-certificates ARCHIVE_DIR=/path/to/archives` | 全アーカイブを確認し，証明書ソースを展開・照合 |
| `make review-files` | ソース収録一覧と日英READMEを確認 |

## ディスク使用量とオプション

以下は，以前の版で行ったビルドの実測値です．両サイズのソースと生成物を含みます．数値はファイルサイズの合計で，1 GBを1,000,000,000バイトとしています．

| ファイル | 実測サイズ |
|---|---:|
| 展開した6×6の証明書ソース | 8.92 GB |
| ビルドで追加されるファイル（オブジェクト，プラグイン，ログ，ビルド記録を含む） | 32.24 GB |
| ハードリンクを一度だけ数えたソースとビルドファイルの合計 | 約41.2 GB |

`.vo` だけで32.21 GBあります．配布物には含めませんが，ビルド中に生成されます．
大きな証明書ソースはビルド先へハードリンクするため，そこでさらに8.92 GBを消費することはありません．
6×6の証明書ソースとビルド先は同一ファイルシステムに置いてください．ハードリンクを作れない場合は停止します．

**6×6の初回ビルド用に，ソース展開後に70 GB以上の空き容量を確保してください．**
事前確認では出力用に50 GB，さらに余裕として20 GBを見込みます．
展開前には，展開するソースとこのビルド用容量を合わせた約80 GBに加え，ダウンロードする圧縮アーカイブの保存容量約2.92 GBを見込んでください．
Rocq・OCamlのインストール領域やOSのスワップ使用量は，これらの数値に含みません．
実際のディスク割当量はファイルシステムに依存します．一時的な使用量のピークは未測定で，70 GBは実測ピークではなく事前確認のための見積もりです．
再開時は，ビルド済みオブジェクトのサイズを差し引いて追加容量を見積もります．

`BUILD_DIR=/path/to/build` で出力先を指定できます．
証明書ソースが別の場所にある場合は `CERTIFICATE_SOURCE=/path/to/sources` を指定します．その直下に `6x6/InitialLower/` など，配布案内に記載した証明書ディレクトリがある場所を指定してください．一覧のソースだけを読み，その場所のコンパイル済みファイルは使いません．
`JOBS=4`・`LINK_JOBS=1`・`INTERFACE_JOBS=4` は，それぞれ証明書ブロック，結合のバッチ，データと接続用モジュールの並列数の既定値です．
6×6のビルドは数十GBのメモリを使うことがあります．
`MODULE_TIMEOUT=1800` は通常の各Rocqコンパイルと4×4のカーネル再検査の秒数上限で，0で解除します．
6×6全体の公理監査・カーネル再検査と，並列結合バッチにはこの上限を設けていません．

証明の構成は [4x4/README-ja.md](4x4/README-ja.md)・[6x6/README-ja.md](6x6/README-ja.md)・[proofs/README-ja.md](proofs/README-ja.md) にあります．
[distribution/verification.json](distribution/verification.json) に検査範囲と結果を記録します．
