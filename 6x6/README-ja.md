# 6×6 Othello：ゲームの値−4

[English](README.md) | [日本語](README-ja.md)

標準初期局面から黒が先手で始め，双方が最善手を選び続けると，終局時の黒石数−白石数は−4です．
白のどの応手に対しても黒は−4以上を保証でき，黒のどの応手に対しても白は−4以下を保証できます．この最善手による対局の石数差を「ゲームの値」と呼びます．

[solutions/Othello6x6.v](../solutions/Othello6x6.v) に初期盤面と問題の解答があります．
`optimal_line` は，記録された対局の32手すべてが最善手であり，黒16石・白20石で終わることを示します．
`value_unique` はゲームの値の一意性を証明します．
`every_optimal_line_has_score_minus_four` は，`optimal_replay` を満たす，終局までの有限の対局について，終局時の石数差が−4になることを証明します．この定義では，各着手・強制パスが合法で，ゲームの値を保つことを求めています．
黒16石・白20石という個別の石数は，示した対局について証明しています．一般の対局についての定理が示すのは石数差です．

**6×6の主定理をビルド・検査するには，Git内のソースと別添の証明書ソースの両方が必要です．**
5個の別添アーカイブには，黒と白の具体的な戦略データと，それを検査して組み合わせる証明を収録しています．
これらのファイルも証明の一部であり，Git内のソースだけでは主定理をビルド・検査できません．

## 証明書データの作成方法

開発時には，Cプログラム `search6_v2.c` と `export_strategy6_v2.c` をRocqとは別に実行し，戦略を探索して記録しました．
`make_block_proof.py` などのPythonプログラムで，記録したデータをRocqのソースファイルに変換しました．
これらの探索・変換プログラムと中間データベースは配布物に含めていません．
証明の再ビルドと検査には，別添の証明書アーカイブに収録した生成済みのRocqソースを使います．ビルド時に元の探索をやり直す必要はありません．

「戦略の証明書」は，自分の手番で選ぶ手と，相手の全合法手を記録したデータです．
同じ局面のデータを共有し，有向非巡回グラフ（DAG）として表します．
Rocqで分割して検査できるよう，証明書を「ブロック」と呼ぶ小さな単位に分けています．
あるブロックが別のブロックの結果を使うときは，その結果の証明を渡します．この結合の証明により，各部分が一つの有限の戦略を構成することを示します．

## 証明とファイル

検証器は，選択した手と相手の全合法手について着手後の盤面を計算し，強制パスと終局時の石数差を検査します．
白が保証する石差の上限は，黒がc2に置いた後の局面で検査します．対称性を使い，黒の4通りすべての合法な初手に結論を広げます．座標は，列を左からa〜f，行を上から1〜6とします．

| 部分 | ファイル |
|---|---|
| ルールと戦略 | [Rules.v](Rules.v)，[Bounds.v](Bounds.v)，[Replay.v](Replay.v)，[Semantics/](Semantics/) |
| 石数差と最善手による対局の証明 | [CertificateResult.v](CertificateResult.v)，[OptimalPlay.v](OptimalPlay.v) |
| ルールの検査例 | [RulesExamples.v](RulesExamples.v) |
| 証明で用いる対称性 | [Symmetry.v](Symmetry.v)，[InitialSymmetry.v](InitialSymmetry.v) |
| DAGとブロックの検証器 | [Dag.v](Dag.v)，[BlockDag.v](BlockDag.v)，[CutDag.v](CutDag.v) |
| 高速な盤面操作 | [GridExp/](GridExp/) |
| ブロック間で渡す局面と検査結果 | [ExportExp/](ExportExp/) |
| 証明書の結合 | [LinkExp/](LinkExp/) |
| 共通定義との一致 | [proofs/equivalence/Six.v](../proofs/equivalence/Six.v)，[proofs/certificates/Six.v](../proofs/certificates/Six.v) |

[OptimalPlay.v](OptimalPlay.v) は指定した棋譜の全33局面のゲームの値を証明します．
検証器の健全性と，高速な盤面表現がルールに一致することもRocqで証明しています．

証明書の検証器は，リストで盤面を表すルールを基準にしています．共通定義との関係は[共通ルールの説明](../common/README-ja.md)を参照してください．
ビット盤面は，石があるマスを整数の各ビットで表したものです．各マスから各方向に延びるマス列も，あらかじめ計算して保存します．
これらにより繰り返し行う盤面操作を速くし，リストで表したルールとの一致をRocqで証明しています．
圧縮は保存するデータを小さくし，ブロック間の結合は分割して検査した結果を組み合わせるために使います．

別添ソースアーカイブには，次の証明書と結合の証明を収録しています．

| 証明書 | 戦略DAGのノード数 | 分割数 | ディレクトリ |
|---|---:|---:|---|
| 黒の下界−4 | 43,160,560 | 1,439 | `InitialLower/`，`InitialLowerCompact/` |
| c2の後の白の上界−4 | 118,749,546 | 1,320 | `InitialUpper/`，`InitialUpperLocalCompact/` |

上界の証明書では，ブロック間の参照を減らすため，短い終盤のデータを各ブロック内に重複して持たせています．そのため，検査するデータは146,623,347件となり，共有されたDAGのノード数より多くなります．
[証明書一覧](../distribution/certificates.tsv) と [配布案内](../distribution/README-ja.md) を参照してください．

## ソースからビルドする

Rocq 9.2 / OCaml 5.3.0，Python 3.11以降，GNU make，同じツールチェインの `ocamlfind`・`ocamlopt` を使用します．

**この6×6の解答の初回のビルド・証明検査には数時間を見込んでください．**
ソースからビルドした際の実測時間と設定は，[ルートのビルド手順](../README-ja.md#checking) にあります．

**ビルドスクリプトは，6×6の初回ビルド前に，ソース展開後の空き容量が70 GB以上あることを確認します．**

5個全ての証明書アーカイブを入手し，[取得・展開手順](../distribution/README-ja.md#certificate-archives)に従って展開してください．
ソースを用意した後，リポジトリのルートから次を実行します．

```text
make check-disk
make check-certificate-files
make check-6x6
```

このプロジェクトのコンパイル済みライブラリは配布せず，入力としても不要です．基礎ルール，OCamlプラグイン，証明書ブロック，結合，最終結果，共通定義で表した解答をビルドします．
使用するのは配布一覧のプロジェクトソースと，インストール済みのRocq・OCamlツールチェインだけです．
環境から引き継いだ追加ライブラリの検索先の設定を解除し，ユーザーのRocq起動ファイルも読みません．
ビルドの出力とキャッシュ記録は，既定では `_build/` に置きます．
中断後も同じコマンドで再開できます．そのビルドで成功したモジュールは，ソースとオブジェクトを確認してから再利用します．
新規または空のビルドディレクトリを要求する場合は，`FRESH=1` を追加してください．

記録した両サイズのビルドでは，追加されたファイルは約32.24 GB，ソースとビルドファイルの合計は約41.2 GBでした．
70 GBの空き容量はソース展開後に必要な量で，出力用50 GBと余裕20 GBを合わせた値です．
展開前には約80 GBに加え，圧縮アーカイブの保存容量約2.92 GBを見込んでください．ツールチェインとOSのスワップ使用量は別途必要です．
証明書ソースは同一ファイルシステム内のビルド先へハードリンクするため，8.92 GBのソースをもう一組コピーしません．
実測値の内訳と範囲は，[ディスク使用量の説明](../README-ja.md#disk-use) を参照してください．一時的な使用量のピークは未測定です．
数十GBのメモリを使うことがあります．
`BUILD_DIR=/path/to/build`・`CERTIFICATE_SOURCE=/path/to/sources`・`ROCQ=/absolute/path/to/rocq` や並列数については [ルートの手順](../README-ja.md#checking) を参照してください．

## 追加検査と記録

| コマンド | 範囲 |
|---|---|
| `make audit-6x6` | ビルド後，主定理と全依存先の公理を監査 |
| `make kernel-6x6` | ビルド後，全体をカーネルで再検査 |

ソースだけからのビルドでは，証明書ブロック，それらを結合する証明，主定理までコンパイルしています．通常のコンパイルで，生成された証明項を検査します．
現在のソースについては，検査済みの証明書のコンパイル結果を再利用して，変更した証明とそれに依存する主定理をコンパイルし，整形による変更はRocqのトークン列の照合で確認しています．現在の6×6のソース全体を最初から再ビルドする検査は行っていません．
上の二つのコマンドは追加検査です．公理監査は定理の公理への依存を調べ，カーネルによる再検査は保存済みのコンパイル結果の証明を改めて検査します．
これらは `make check-6x6` に含まれず，6×6全体についてはいずれも未実行です．
[verification.json](../distribution/verification.json) に，ソースだけからの再ビルドと実行した検査を記録します．
